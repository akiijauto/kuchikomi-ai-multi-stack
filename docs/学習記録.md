### 設計判断と、その理由

**1. なぜマルチステージにしたか**
単一ステージだと実行イメージに開発依存（TypeScript / ESLint / Tailwind のビルド系）と
ソースコードがそのまま残る。イメージが大きくなるだけでなく、本番コンテナに
ビルドツールが同居する状態はセキュリティ上も望ましくない。
`deps` を分けたのは、`package*.json` が変わらない限り `npm ci` の層をキャッシュさせるため。

**2. なぜ `output: "standalone"` が必要か**
これが無いと `next start` の実行に `node_modules` 全体が要る。`standalone` は
実際に使われている依存だけを `.next/standalone` に自己完結の形で出力するので、
実行ステージへは `standalone` / `static` / `public` の3つをコピーするだけで済む。

**3. NEXT_PUBLIC_* をなぜ ARG で渡すのか（詰まった点）**
`NEXT_PUBLIC_*` は**ビルド時にクライアントJSへ文字列として焼き込まれる**。
つまり実行時に `-e` で渡しても差し替わらない。したがって
- 公開値（Supabase URL / anon key / 運営者名）→ `ARG` としてビルド時に渡す
- 秘密鍵（`ANTHROPIC_API_KEY` / `STRIPE_SECRET_KEY` / `SUPABASE_SERVICE_ROLE_KEY`）→ 実行時に `env_file` で注入
と経路を分けた。ダミー既定値を置いてあるので、鍵が無い環境でもイメージのビルド自体は通る。

**4. ヘルスチェックを認証基盤から切り離した理由**
このアプリの `proxy.ts`（Next.js 16 のミドルウェア）は全パスで Supabase に
`auth.getUser()` を投げる。ヘルスチェックがその経路を通ると、
「アプリは生きているが Supabase が不調」のときにコンテナごと unhealthy と判定され、
再起動ループに入りうる。切り分けができる状態を保つため matcher から除外した。

**5. 素の Postgres で Supabase のスキーマを流すために必要だったもの**
`web/supabase/schema.sql` は `auth.users` への外部キー、`auth.uid()`、
`anon` / `authenticated` ロールへの grant に依存している。素の postgres:16 には
どれも無いため、`00_supabase_compat.sql` でその3つだけを最小限用意した。
認証の再現が目的ではなく、**スキーマ・制約・関数をローカルで検証できる**状態を作るのが目的。

**6. ベース＝本番相当 / override＝開発 にした理由**
`docker-compose.override.yml` は `docker compose up` で自動的に重なる。
逆に `docker compose -f docker-compose.yml up` と明示すればベースだけが使われる。
「開発の便利設定（バインドマウント等）が本番構成に混ざらない」ことを構成で担保できる。
compose のリスト項目（volumes 等）は上書きではなく**マージ**されるため、
「本番ファイルでバインドマウントを消す」書き方はできない。この順序が定石。
