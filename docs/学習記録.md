### 設計判断と、その理由

**1. なぜマルチステージにしたか**
単一ステージだと実行イメージに開発依存（TypeScript / ESLint / Tailwind のビルド系）と
ソースコードがそのまま残る。イメージが大きくなるだけでなく、本番コンテナに
ビルドツールが同居する状態はセキュリティ上も望ましくない。
`deps` を分けたのは、`package*.json` が変わらない限り `npm ci` の層をキャッシュさせるため。

**2. なぜ `output: "standalone"` が必要か**
これが無いと `next start` の実行に `node_modules` 全体が要る。`standalone` は
実際に使われている依存だけを `.next/standalone` に自己完結の形で出力するので、
実行ステージへは `standalone` / `static` / `public` の3つをコピーするだけで済む。

**3. NEXT_PUBLIC_* をなぜ ARG で渡すのか（詰まった点）**
`NEXT_PUBLIC_*` は**ビルド時にクライアントJSへ文字列として焼き込まれる**。
つまり実行時に `-e` で渡しても差し替わらない。したがって
- 公開値（Supabase URL / anon key / 運営者名）→ `ARG` としてビルド時に渡す
- 秘密鍵（`ANTHROPIC_API_KEY` / `STRIPE_SECRET_KEY` / `SUPABASE_SERVICE_ROLE_KEY`）→ 実行時に `env_file` で注入
と経路を分けた。ダミー既定値を置いてあるので、鍵が無い環境でもイメージのビルド自体は通る。

**4. ヘルスチェックを認証基盤から切り離した理由**
このアプリの `proxy.ts`（Next.js 16 のミドルウェア）は全パスで Supabase に
`auth.getUser()` を投げる。ヘルスチェックがその経路を通ると、
「アプリは生きているが Supabase が不調」のときにコンテナごと unhealthy と判定され、
再起動ループに入りうる。切り分けができる状態を保つため matcher から除外した。

**5. 素の Postgres で Supabase のスキーマを流すために必要だったもの**
`web/supabase/schema.sql` は `auth.users` への外部キー、`auth.uid()`、
`anon` / `authenticated` ロールへの grant に依存している。素の postgres:16 には
どれも無いため、`00_supabase_compat.sql` でその3つだけを最小限用意した。
認証の再現が目的ではなく、**スキーマ・制約・関数をローカルで検証できる**状態を作るのが目的。

**6. ベース＝本番相当 / override＝開発 にした理由**
`docker-compose.override.yml` は `docker compose up` で自動的に重なる。
逆に `docker compose -f docker-compose.yml up` と明示すればベースだけが使われる。
「開発の便利設定（バインドマウント等）が本番構成に混ざらない」ことを構成で担保できる。
compose のリスト項目（volumes 等）は上書きではなく**マージ**されるため、
「本番ファイルでバインドマウントを消す」書き方はできない。この順序が定石。

### やったこと

`infra/` に Terraform で構成一式を書いた（`terraform validate` 通過）。

| ファイル | 内容 |
|---|---|
| `versions.tf` | provider定義。stateはローカル（1人・1台のため） |
| `variables.tf` | region / 公開範囲 / イメージタグ / 秘密値 |
| `network.tf` | VPC・パブリックサブネット×2・IGW・SG2種 |
| `ecr.tf` | リポジトリ＋直近3イメージのみ保持するライフサイクル |
| `rds.tf` | PostgreSQL 16 / db.t4g.micro。パスワードは生成 |
| `s3.tf` | パブリックアクセス4項目遮断＋暗号化 |
| `secrets.tf` | SSMパラメータストア(SecureString) |
| `ecs.tf` | クラスタ・ロググループ・IAM2種・タスク定義・サービス |
| `deploy.sh` / `status.sh` / `logs.sh` | ビルド〜デプロイ〜IP確認〜ログ追跡 |

### 設計判断と、その理由

**1. NATゲートウェイとALBを置かなかった**
NATは月$40前後、ALBは月$20前後の**固定費**。$10予算では、実働時間に関係なく
これだけで破綻する。代わりにECSタスクをパブリックサブネットへ置き、
`assign_public_ip = true` でタスク自身に公開IPを付けた。
**引き換えに失うもの**: TLS終端が無い（HTTPになる）、タスク再起動ごとにIPが変わる、
デプロイ中に無停止にできない。学習用と割り切り、`allowed_cidr` で公開範囲を絞る前提にした。

**2. RDSの公開範囲をCIDRではなくセキュリティグループ参照にした**
サブネットはパブリックだが、DBのSGは `referenced_security_group_id = アプリのSG` にしてある。
IPレンジで書くと「たまたまそのレンジに入った別のもの」まで届くが、SG参照なら
到達できるのはアプリのタスクだけになる。パブリックサブネットに置かざるを得ない構成では
ここが実質的な防御線。

**3. Secrets Manager ではなく SSM パラメータストアにした**
Secrets Managerは1件$0.40/月。3件で月$1.2は$10予算では無視できない。
SSM Standard の SecureString は無料で、ECSの `secrets` ブロックから同じように読める。
**タスク定義に平文が載らない**という肝心の性質は同じ。

**4. DBパスワードを人が決めない**
`random_password` で生成し、そのままSSMへ。人の目にも、コミットにも、
チャットにも一度も現れない。URLに入れるため記号は `-_` だけに限定した
（`@` や `/` が入るとURLが壊れるため）。

**5. IAMロールを2つに分けた**
実行ロール（ECSの仕組み側：イメージpull・ログ出力・SSM読み取り）と、
タスクロール（アプリのコード自身：S3アクセス）は用途が違う。
1つにまとめると、アプリのコードがSSMの秘密値を読める権限まで持ってしまう。

### 詰まった点の記録

**`terraform validate` が2件の実エラーを出した（書いただけでは気づけなかった）**

1つ目: **sensitive な値から作ったマップは `for_each` に渡せない**。
`{ANTHROPIC_API_KEY = var.anthropic_api_key, ...}` のように値がsensitiveだと、
マップ全体がsensitive扱いになる。for_eachのキーはstateにリソースアドレスとして
現れるため、Terraformが拒否する。
→ 「作る名前の集合」と「値の対応表」を分け、名前の集合だけ `nonsensitive()` で
取り出す形に直した。明かしているのは**そのキーを設定したかどうか**だけで、値ではない。

2つ目: localのリネームで `local.app_secrets` への参照が壊れていた。
`DATABASE_URL` は常に作られるので、そもそもcountでの分岐が不要だった。

**この2件は、書いた本人が読み返しても見つけにくい種類の誤り。**
検証コマンドを持っている意味がここにある。CIにも `terraform fmt -check` と
`terraform validate` を追加し、以後は壊れたまま気づかない状態にならないようにした。

### 追記 2026-09-03: デプロイ経路をローカルからCIへ移した

**きっかけ**: ローカルの Docker Desktop を打ち切ったことで、`deploy.sh`（ローカルで
`docker build` → ECRへpush）が**このPCでは実行できなくなった**。AWSへ何かを載せるには、
まずイメージを作れる場所が要る。

**やったこと**: `github_oidc.tf` と `.github/workflows/deploy.yml` を追加し、
ビルドとpushをGitHubのランナーで行う経路に置き換えた。

| 設計判断 | 理由 |
|---|---|
| アクセスキーをGitHub Secretsに置かず**OIDC**にした | 長期キーは漏れても失効まで有効で、漏れたこと自体に気づけない。OIDCはGitHubが出す数分の短命トークンをAWSが直接検証するので、**保存する秘密が存在しない**。IAMなので無料 |
| `sub` 条件でリポジトリを絞った | これを省くと「GitHub上のどのリポジトリのワークフローからでも」このロールを取れてしまう。`repo:owner/name:*` に限定した |
| タスク定義の再登録をせず `--force-new-deployment` だけにした | 再登録を許すと `iam:PassRole` が要る＝CIがECSのロールを渡せる権限まで持つ。タスク定義は `latest` を見ているので、latestを差し替えて再デプロイさせれば足りる |
| それでもコミットハッシュのタグを併せてpushする | `latest` は動くので「今動いているのがどのコードか」を後から追えない。追跡用に `:<sha>` も残す |
| 自動デプロイ（push: main）にせず `workflow_dispatch` にした | $10予算のため確認が済んだら毎回 `terraform destroy` する運用。インフラが無い状態でmainにpushするたび失敗が並ぶと、CIの赤が意味を持たなくなる |

`terraform validate` 通過。ロールのARNは `github_deploy_role_arn` として出力するようにし、
apply後に `gh variable set AWS_DEPLOY_ROLE_ARN` で渡すだけで繋がる状態にした。

### 2026-09-03: apply からデプロイまで一気通貫で通した

認証情報が入ったので `plan` → `apply` → デプロイ → 動作確認まで実施した。**33リソースを作成**。
動いているアプリに外から接続でき、`/api/health` が `{"status":"ok"}` を返し、トップページも200を返した。

#### 詰まった点1: AWSへ送る説明文に日本語を入れていた

`terraform apply` が2箇所で止まった。

```
InvalidParameterValue: Invalid rule description. Valid descriptions are
strings ... from the following set:  a-zA-Z0-9._-:/()#,@[]+=&;{}!$*
```

セキュリティグループのルールとIAMロールの `description` に日本語を書いていた。
**AWSに渡る文字列と、コードを読む人向けの説明は別物**。前者は英数字にし、
意図はコメントへ移した。`terraform validate` では見つからない種類の誤りで、
実際にAPIへ投げて初めて分かった。

#### 詰まった点2: OIDCの信頼条件が一致せず、3回連続で弾かれた

```
Could not assume role with OIDC: Not authorized to perform sts:AssumeRoleWithWebIdentity
```

原因を推測で潰そうとして2回外した。**推測をやめてトークンの中身を実測したら一発で分かった。**
一時的な診断用ワークフローで、トークンのクレームだけを取り出して表示した:

```
sub = repo:akiijauto@288162362/kuchikomi-ai-multi-stack@1352683534:ref:refs/heads/main
```

`repo:owner/name:*` という**古い形式しか許可していなかった**。実際のGitHubは
所有者IDとリポジトリIDを埋め込んだ新形式を送ってきていた。
数値IDは名前と違って**後から付け替えられない**ので、本来はこちらの方が厳しい条件になる。
新旧どちらでも通るよう両方を許可した。

**副産物**: 途中で疑った証明書の拇印も、実測すると古い値のままだった。
GitHubの証明書はDigiCertからLet's Encryptに変わっており、コードにベタ書きしていた拇印は
チェーンのどれとも一致しなかった。**更新されうる値を定数で書かない**方針に変え、
`tls_certificate` データソースで実物から取るようにした。これは今回の直接原因ではなかったが、
放置すればいずれ同じ形で壊れる。

| 学び | 内容 |
|---|---|
| 推測で3回試すより、1回測る | 症状から原因を当てにいって2回外した。クレームを表示させたら即座に確定した |
| 認証の失敗メッセージは詳細を教えてくれない | 「許可されていない」としか言わない。**どの条件で落ちたかは自分で調べるしかない** |
| 定数で書いた外部の値は、いつか合わなくなる | 拇印もsubの形式も、書いた時点では正しかった |

ステータスコードとエラー文言はNext.js版に合わせた。同じ画面から差し替えて呼べる状態。

### 設計判断と、その理由

**1. Railsのマイグレーションを作らなかった**
テーブル定義の正本は `web/supabase/schema.sql` のままにし、Rails側からは既存の表を使うだけにした。
Railsに `db/migrate` を書くと**同じ表の定義が2箇所に増える**。この演習の主旨は
「同じスキーマに別言語の実装を載せる」ことなので、定義を複製する理由がない。

**2. 利用回数の上限判定をRubyに持ってこなかった**
DBの `public.increment_usage` をそのまま呼んでいる。
「今の件数を読む→判定→書く」をアプリ側で書くと、同時に2本来たときに上限を超えられる。
DB関数は1文で判定と加算を行うので、**実装言語が変わっても保証が変わらない**。
Next.js版と同じ関数を呼んでいるため、上限の挙動は自動的に一致する。

`increment_usage` の中の `auth.uid()` はセッション変数から読む作りなので、
呼ぶ前に `set_config('request.jwt.claim.sub', <id>, true)` を立てている。
第3引数の `true` はトランザクション内限定という意味で、接続を使い回しても他のリクエストに漏れない。

**3. 認証はJWTを自前で検証した**
Next.js版は `supabase-js` の `auth.getUser()` が裏でやっている。Railsにその依存は無いので、
Supabaseが発行したJWTを `jwt` gem で検証している。やることは同じで、
「署名が正しいか」と「誰なのか（`sub`）」を取り出すだけ。

**4. RLSを当てにせず、Rails側でも自分の行に限定した**
本番のSupabaseでは行レベルセキュリティが最後の砦になる。しかしRailsが**テーブル所有者の
ロールで接続すると、RLSは素通りする**。同じスキーマでも、**誰として接続するかで守りが変わる**。
`Profile.find_by(id: current_user_id)` で絞っているのは飾りではない。
テストでも「他人の行が変わらないこと」を確認している。

### 詰まった点の記録

**「作る」つもりが既にあった**
テストヘルパで `auth.users` に挿入したあと `Profile.create!` したところ、主キー重複で11件が落ちた。
原因は `schema.sql` の `on_auth_user_created` トリガーで、
**auth.users への挿入時点で profiles の行が自動で作られていた**こと。
作成ではなく更新に直して解消。落ちたおかげでトリガーが効いていることの確認にもなった。

**SDKの引数名は推測せず実物を見た**
Ruby SDKは `system:` ではなく `system_:`（`Kernel#system` と衝突するため）、
構造化出力は `format:` ではなく `format_:`（送信時に `format` へ変換）。
`gem environment gemdir` から実物の定義を読んで確認した。TypeScript版の書き方から
推測していたら、鍵が無い環境では気づけないまま埋め込んでいた（CIはデモ経路しか通らないため）。

### 検証状況（CIで実施。ローカルにPostgreSQLが無いため）

## 環境トラブル: Docker が全コマンド500を返す（2026-09-03 調査）

Week5へ進む前に `docker` が動かなくなった。**原因はこのリポジトリではなく Windows 側**だったので、
同じ症状に再会したときのために切り分けの筋道を残す。

> **前提（先に読むこと）**: 2026-09-03 の判断で **ローカルの Docker Desktop は使わない**ことにしており、
> Docker の検証はすべて GitHub Actions のジョブで行っている（Week1 は CI でホットリロードまで実証済み）。
> **したがって、この不具合はカリキュラムの進行を止めない。** 以下は「直さないと進めない話」ではなく、
> *ローカルで Docker を使いたくなったときのための* 原因記録である。

### 症状

```
docker ps -a
→ request returned 500 Internal Server Error for API route and version
  http://%2F%2F.%2Fpipe%2FdockerDesktopLinuxEngine/v1.55/containers/json?all=1
```

`docker version` も同じ。クライアント側の情報は出るがサーバー側だけ500。
Docker Desktop のプロセス（Docker Desktop / com.docker.backend）は起動している。

### 切り分けの順序

**「500 = サーバーは居るが壊れている」ではなかった。** 名前付きパイプに応答があるので
デーモンが居るように見えるが、実際には*外側のバックエンドだけ*が応答していた。
Docker Desktop 自身のログ（`%LOCALAPPDATA%\Docker\log\`）が決定的だった。

| 見たもの | 内容 |
|---|---|
| `host/docker-desktop.exe.log` | `{"docker":"stopped","dockerAPI":"stopped","hasNoVirtualization":true,"state":"stopped"}` |
| `host/com.docker.backend.exe.log` | `cannot toggle VM OTel collector, backend is not running` が21時間継続 |
| `vm/init.log` | 空。**Linux VM が一度も起動していない** |

`hasNoVirtualization: true` から Windows 側へ降りた。

### 根本原因

Docker Desktop は WSL2 バックエンド（インストーラログに `--backend=wsl-2`）。その WSL2 が動けない。

| 実測項目 | 結果 |
|---|---|
| `wsl -l -v` | ディストリビューション0件 |
| Lxss レジストリ | distro無し。`InstallStatus = VirtualMachinePlatform` のみ |
| `System32\vmcompute.exe` | **存在しない**（`vmwp.exe` も） |
| `vmcompute` サービス | NOT_INSTALLED |
| `VirtualMachinePlatform`（WMI） | Enabled(1) |
| CBS RebootPending / PackagesPending | True / True（保留 11,522件） |
| 稼働時間 | 21時間35分（最終起動 09-03 01:49） |

**Windows のコンポーネント更新が「適用途中・再起動待ち」で止まっている**
→ VM を作る Host Compute Service（`vmcompute.exe`）がまだディスクに無い
→ WSL2 が VM を作れない → Docker の Linux VM が起動しない → 全 docker コマンドが500。

ハードウェア側の仮想化は正常（`VirtualizationFirmwareEnabled=True`、VBS稼働、ベアメタル）。
**BIOS を触る必要は無かった。**

### 学んだこと

**1. WMI の `Enabled` は「入っている」ではなく「入れる予定」だった**
`VirtualMachinePlatform` は Enabled(1) と返るのに `vmcompute.exe` が実在しない。
機能の有効/無効を問い合わせるだけでは足りず、**その機能が置くはずの実体を確認する**必要がある。
今回は「サービスの有無」と「exeの有無」で矛盾に気づけた。

**2. 「仮想化が無効」というメッセージを額面で受け取らない**
`wsl --status` は firmware の仮想化設定を疑わせる文言を出すが、実際は firmware は有効だった。
メッセージの指す先（BIOS）へ直行していたら、再起動という正解に届かないまま時間を溶かしていた。

**3. アプリのログより先に、アプリが依存する層のログを見る**
compose ファイルやプロジェクトのDockerfileを疑っても何も出なかった。
`api-rails/` は compose に未接続なので、そもそも今回の500とは無関係。

### 対処（未実施・急ぎではない）

上の前提のとおりローカル Docker は使わない方針なので、**この対処は必須ではない**。
ローカルで Docker を動かしたくなったときにだけ実施すればよい。

**PC の再起動**で保留中の servicing が適用される。保留 11,522件のため時間はかかる。
再起動後の確認順序: `vmcompute.exe` の有無 → `wsl --status` → `docker version` → `docker compose up`。
初回は Docker Desktop が `docker-desktop` ディストロを作り直すため1〜2分かかる。

それでも直らない場合は管理者PowerShellで `wsl --install --no-distribution` → 再起動
（`Microsoft-Windows-Subsystem-Linux` 機能が Disabled のため）。ただしStore版WSL 2.7.12 は
VirtualMachinePlatform だけで動くので、**まず再起動だけで済む見込み**。

### 追記 2026-09-03: Rails APIをAWSへ載せ、ブラウザから触れる形にした

Week4の成果はAPIだけで画面が無く、「動いている」ことを見せられなかった。
コンテナ化してAWSへ載せ、`public/demo.html` から実際に生成を試せる状態にした。

#### 構成

Next.js版と**並べて**動かしている。Rails習得カリキュラムが Week4〜5 の題材に挙げている
「Next.jsフロント＋RailsバックエンドAPI」の形に近い。

| 追加したもの | 内容 |
|---|---|
| `infra/ecs_rails.tf` | ECRリポジトリ・タスク定義・サービス。SGとRDSは既存を共用 |
| `api-rails/lib/tasks/bootstrap.rake` | スキーマ投入。`LOAD_SCHEMA=1` のとき起動時に走る |
| `api-rails/public/demo.html` | 口コミを入力して3案を受け取れるデモ画面 |
| `api-rails/app/controllers/api/demo_controller.rb` | デモ用トークン発行。`DEMO_MODE=1` のときだけ経路が生える |

#### 設計判断

**1. スキーマの投入をコンテナ自身にやらせた**
RDSは `publicly_accessible = false` で、手元からpsqlで流せない。
ロードバランサも踏み台も置いていないので、VPC内にいるのはアプリのタスクだけ。
そのタスクに流させるのが一番素直だった。
SQLの正本は複製せず、**ビルドの直前にコンテキストへコピーする**形にしている
（`api-rails/db/bootstrap/*.sql` はgit管理外）。

**2. `SECRET_KEY_BASE` をSSMから渡し、`master.key` をイメージに焼かなかった**
master.key をイメージへ入れると、イメージを取得できる人が資格情報を全部読める。
Railsは `SECRET_KEY_BASE` を直接渡せば credentials を読まずに起動できる。

**3. SSL強制を環境変数で切り替えられるようにした（既定は有効のまま）**
Rails 8 の production は `force_ssl = true` が既定。この構成にはTLS終端が無いため
全リクエストがhttpsへ転送されて繋がらない。
**既定値そのものは変えていない**。既定をfalseにすると、後で本物の本番を作ったときに
「SSLが切れていることに気づかない」状態になるため。

**4. デモ用の口はコントローラではなくルーティングで塞いだ**
`DEMO_MODE=1` のときだけ `post "demo/token"` を定義する。
コントローラ内で判定する形にすると、設定を間違えたときに経路が生きたままになる。
これは「誰でもログイン済みになれる入口」なので、存在しないことが保証される側に倒した。

#### 詰まった点: 400が返るのはアプリのせいではなかった

デプロイ後、`POST /api/generate` が本文空の **400** を返した。CIでは同じリクエストが
401を返していたので、環境差を疑って調べ始めた。

切り分けの決め手は**本文をASCIIに変えたら401が返った**こと。日本語のときだけ400になる。
ログの `req_content_length` が **49バイト**で、UTF-8なら54バイトになるはずだった。
つまり**こちらのシェルが日本語をUTF-8以外で送っていた**。
UTF-8で書いたファイルから `--data-binary` で送ると、正しく3案が返った。

**壊れていたのは測定器のほうだった。** アプリは最初から正しく動いていた。
「環境差だ」と決めつけて設定をいじり続けていたら、直っていないものを直そうとして
別のものを壊していた可能性が高い。バイト数が合わないことに気づけたのが分かれ目だった。

#### 検証（2026-09-03 実測）

| 確認項目 | 結果 |
|---|---|
| Railsコンテナが起動しRDSへ接続できるか | ✅ |
| 起動時にスキーマが投入されるか（LOAD_SCHEMA） | ✅ 3表と関数が作られた |
| `/api/health` | ✅ 200 |
| `/demo.html` が配信されるか | ✅ 200 |
| デモ用トークン発行 → 生成 | ✅ 返信案3件、利用回数1件加算 |
| 認証なしの拒否 | ✅ 401 |
| Next.js版も同時に動くか | ✅ 200（別タスク・別IP） |

APIキーを渡していないため生成はデモ返信（`mock: true`）。経路は本番と同じ。
